CV Specialization & Tailoring Skill
Purpose

This skill defines how to create, tailor, review, and improve CVs for software engineering and technology roles.

The primary objective is to ensure that every CV communicates a clear professional specialization rather than presenting the candidate as a generic software engineer with an unnecessarily broad collection of technologies.

The CV must make it immediately clear:

What type of engineer the candidate is.
What technical area they specialize in.
What technology stack they are strongest in.
What evidence proves that specialization.
What type of role the CV is targeting.

The CV should make the recruiter understand the candidate's professional identity within a few seconds.

1. Core Principle: Pick a Niche

A CV must not attempt to target every possible software engineering position simultaneously.

Instead:

One CV = One primary professional identity = One target role family.

Examples:

Backend Software Engineer
Python Backend Developer
Java Backend Developer
Full-Stack Developer
React Frontend Developer
DevOps Engineer
Cloud Engineer
Embedded Software Engineer
Computer Networking Engineer
AI/ML Engineer
Data Engineer
Cybersecurity Engineer

A candidate may have experience across several areas, but each CV should emphasize the area most relevant to the position being targeted.

The CV must answer:

immediately.

4. The Primary CV Rule

Every CV must have one clearly identifiable primary specialization.

The following test must pass:

If someone reads only the CV headline, summary, first experience/project entries, and top skills, they should be able to identify the target specialization without guessing.

If they cannot, revise the CV.

5. Do Not Create a Generic "Everything" CV

Avoid creating a CV that tries to equally represent:

Backend + Frontend + Embedded + Networking + DevOps + AI + Cybersecurity

unless the specific position genuinely requires that combination.

Instead, create specialized CV variants.

For example:

CV/
├── Backend Software Engineer
├── Python Backend Developer
├── Full-Stack Developer
├── Embedded Software Engineer
├── DevOps / Cloud Engineer
├── Networking / Systems Engineer
└── AI / Data Engineer

The same candidate can therefore maintain several targeted CVs without changing their underlying career history.

6. Evidence-Based Specialization

A specialization must be supported by evidence.

Do not claim:

Expert Python Engineer

Instead, demonstrate Python through:

Professional experience
Projects
APIs
Backend systems
Automation
Testing
Databases
Infrastructure
GitHub repositories
Relevant coursework
Certifications
Measurable outcomes

The stronger the evidence, the stronger the specialization.

7. Skills Must Support the Target

The Skills section should not be a technology inventory.

Every skill should answer one of these questions:

Is this directly relevant to the target role?
Does this demonstrate the candidate's specialization?
Is this supported by experience or projects?
Is this likely to appear in the job description?
Does this strengthen the candidate's technical identity?

If the answer is no to most of these questions, consider removing the skill from that CV version.

9. Headline Strategy

The headline should communicate the specialization directly.

Avoid:

Computer Engineering Graduate | Software Engineer | Developer | Programmer

Prefer a more focused identity such as:

Backend Software Engineer | Python | FastAPI | Django

or:

Python Backend Developer | APIs | Databases | Docker

or:

Embedded Software Engineer | C/C++ | Linux | Microcontrollers

or:

Full-Stack Software Engineer | React | Python | REST APIs

The headline should reflect the CV's target.

10. Professional Summary Strategy

The summary should follow this structure:

[Professional identity] + [primary specialization] +
[technical strengths] + [evidence] + [target role].

Example structure:

Computer Engineering graduate specializing in Python backend
development, with hands-on experience building REST APIs,
database-backed applications, automation workflows, and
containerized services. Experienced with Python, FastAPI,
Django, PostgreSQL, MongoDB, Redis, Docker, and Linux.
Seeking backend software engineering opportunities where I
can contribute to reliable, scalable backend systems.

The summary should not list every technology the candidate has ever touched.

11. Experience Section

Experience bullets must reinforce the specialization.

Use this structure:

Action + Technology + Problem + Result

Example:

Developed REST API endpoints using Python and FastAPI to support
backend application workflows and database operations.

Stronger:

Developed REST API endpoints using Python and FastAPI, integrating
database operations and authentication to support application
workflows.

When genuine measurements exist, use them.

Examples:

Reduced incident-response effort by 60%.
Improved network link utilization by approximately 35%.

However, do not invent metrics.

12. Metrics Rule

Only use quantitative claims that can be supported.

Good:

Reduced incident-response effort by 60%.

if the figure was actually measured.

Use cautious wording for estimates:

Reduced configuration effort by an estimated 80%.

if it was an estimate.

Avoid unsupported claims such as:

Handled 1,000+ concurrent requests

unless this was actually benchmarked.

Avoid:

Achieved 95%+ test coverage

unless coverage was genuinely measured.

The CV must be defensible during an interview.

13. Testing Claims

Do not claim Test-Driven Development if tests were written after implementation.

Instead of:

Applied Test-Driven Development to build reliable services.

use wording such as:

Implemented automated tests to validate application functionality
and reduce regressions.

or:

Developed automated tests alongside application implementation
to improve reliability and maintainability.

The wording must accurately represent what was actually done.

Each project should communicate:

What was built
+
How it was built
+
Why it matters
+
What technical skills it demonstrates

Example:

The project description should emphasize the technologies relevant to the target CV.

17. Tailoring Rule

Do not rewrite the entire career history for every application.

Instead:

Keep:
- truthful experience
- relevant projects
- education
- genuine skills

Change:
- headline
- summary
- skill ordering
- project ordering
- bullet emphasis
- technology emphasis

This creates targeted CVs without creating inconsistent career histories.

18. CV Variant System

Maintain a master CV containing the complete truthful history.

Then create specialized versions.

Example:

MASTER CV
│
├── Backend Software Engineer CV
├── Python Backend CV
├── Full-Stack Developer CV
├── Embedded Software Engineer CV
├── DevOps / Cloud CV
├── Networking Engineer CV
└── AI / Data CV

The master CV is the source of truth.

Specialized CVs are filtered views of the same experience.

20. Education Strategy

Education should support the professional identity without becoming the identity itself.

Instead of making the CV headline:

Computer Engineering Student

use the engineering specialization first when appropriate:

Then list:

BEng Honours in Computer Engineering

under Education.

Education establishes the foundation.

Technical evidence establishes the specialization.

23. ATS Optimization

A specialized CV must still contain the terminology used by the target job description.

Use the employer's terminology where it accurately describes existing experience.

For example, if a job requires:

REST APIs
Docker
PostgreSQL
Python
FastAPI

and the candidate genuinely has those skills, these should appear naturally in:

Summary
Experience
Projects
Skills

Do not keyword-stuff the CV.

24. Recruiter Clarity Test

Before submitting a CV, ask:

Question 1

What type of engineer is this candidate?

The answer should be immediate.

Question 2

What technology are they strongest in?

The answer should be visible.

Question 3

What type of problems can they solve?

The experience and projects should answer this.

Question 4

Does the experience prove the specialization?

If not, change the emphasis.

Question 5

Does the target job match the CV's identity?

If not, create or use another CV variant.

25. Five-Second Test

A recruiter should be able to scan the top portion of the CV and identify:

WHO
↓
WHAT THEY SPECIALIZE IN
↓
WHAT TECHNOLOGIES THEY USE
↓
WHAT THEY HAVE BUILT
↓
WHAT ROLE THEY WANT

If this chain is unclear, the CV needs refinement.

26. Truthfulness Rule

Never modify facts merely to make the CV stronger.

Do not:

Invent metrics.
Invent responsibilities.
Invent employment.
Invent technologies.
Upgrade a beginner skill to expert.
Claim production experience that did not happen.
Claim TDD if tests were written after implementation.
Claim measured performance without measurement.
Claim certifications that were not obtained.

The goal is to make genuine experience clearer, not to manufacture experience.

27. CV Review Procedure

When reviewing an existing CV, perform the following sequence.

Step 1  Identify the Current Identity

Determine what the CV currently appears to say the candidate is.

Step 2  Identify the Target Role

Determine what position the CV should target.

Step 3  Find the Strongest Evidence

Identify the experience and projects most relevant to the target.

Step 4  Remove Noise

Reduce technologies and experiences that distract from the specialization.

Step 5  Rewrite the Headline

Make the target specialization explicit.

Step 6  Rewrite the Summary

Connect:

identity + specialization + stack + evidence + target
Step 7  Reorder Skills

Place the most relevant technologies first.

Step 8  Reorder Projects

Put the strongest evidence for the target specialization first.

Step 9  Validate Metrics

Check every number for accuracy.

Step 10  Perform the Five-Second Test

Verify that the specialization is immediately obvious.

Before submitting any CV, verify:

Positioning

One clear target role.

One primary specialization.

Headline reflects the specialization.

Summary reinforces the specialization.

Technical Stack

Core technologies appear prominently.

Skills are relevant to the target.

No unnecessary technology dumping.

Technologies are genuinely supported.

Experience

Strongest relevant experience appears first.

Bullets demonstrate technical ability.

Results are quantified where genuinely measurable.

Projects

Truthfulness

No keyword stuffing.

Formatting remains readable.

30. Final Principle

The purpose of a CV is not to prove that a candidate has touched every technology.

The purpose is to make the candidate's most valuable and relevant capability unmistakable.

Therefore:

Do not make the CV broader just to qualify for more jobs. Make it clearer so the right jobs can recognize the candidate.

A candidate can maintain multiple specialized CVs while keeping one truthful master record.

The strategy is:

Master Experience
        ↓
Choose Target Role
        ↓
Choose Specialization
        ↓
Select Supporting Evidence
        ↓
Build Specialized CV
        ↓
Tailor to Job Description
        ↓
Validate Every Claim
        ↓
Submit

The strongest CV is not necessarily the one containing the most technologies.
